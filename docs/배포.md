# 외부 접속과 인터넷 서버 배포

## 코치 PC가 켜져 있으면 서버가 열리나요?

**PC·앱·인터넷·HTTPS 외부 연결이 모두 실행 중일 때** 선수가 접속할 수 있습니다. PC 전원만 켜져 있어서는 외부 접속이 자동으로 되지 않습니다. 절전·최대절전·전원 종료·앱/터널 종료·인터넷 장애 중에는 업로드가 중단됩니다.

프로그램은 두 가지 모드를 분리합니다.

| 용도 | 기본 포트 | 로컬 코치 모드 | 외부 연결 |
| --- | --- | --- | --- |
| 코치 PC 전체 관리 | `127.0.0.1:8000` | 켬 | 연결하면 안 됨 |
| 선수 공통 주소 / 선택적 개인 링크 | `127.0.0.1:8001` | 끔 | HTTPS 터널/프록시 연결 |

코치는 로컬 전체 관리 화면에 로그인 없이 접근합니다. **로그인 없는 코치용 8000 포트를 인터넷이나 터널에 연결하면 전체 기록이 노출될 수 있습니다.** 선수를 위한 외부 연결은 반드시 코치 자동접속을 끈 별도 서버로 향해야 합니다. 공유기에서 임의 포트만 열고 평문 HTTP로 공개하지 마세요.

## 선택 A: Windows PC + HTTPS 터널

예를 들어 Cloudflare Tunnel처럼 **외부 HTTPS → 코치 PC의 `http://127.0.0.1:8001`**을 연결하는 서비스를 사용할 수 있습니다. 제공자 계정·도메인·약관·보안 설정이 필요하며 이 저장소에 운영 주소는 들어 있지 않습니다.

1. 로컬 설치·샘플 업로드를 검증합니다.
2. 터널 제공자 공식 지침에 따라 계정·도메인과 영구 터널을 만듭니다. 임시 랜덤 URL은 장기 운영 주소로 쓰지 않습니다.
3. `.env`에 다음을 입력합니다. 예시 도메인과 키를 실제 값으로 바꿉니다.

```dotenv
APP_PUBLIC_URL=https://lesson.example.com
APP_ALLOWED_HOSTS=localhost,127.0.0.1,lesson.example.com
APP_CSRF_TRUSTED_ORIGINS=https://lesson.example.com
APP_SECRET_KEY=여기에_새로_생성한_충분히_긴_무작위_키
```

비밀키 생성 명령: `python -c "import secrets; print(secrets.token_urlsafe(64))"`. 예시 문자열을 그대로 쓰지 않습니다.

4. 코치용 `start_windows.bat`를 계속 실행한 상태에서 별도 창에 `start_share_windows.bat`를 실행합니다. 공유 스크립트는 `APP_LOCAL_COACH=0`, `APP_DEBUG=0`, `APP_SECURE=1`, `APP_TRUST_PROXY=1`을 강제로 지정합니다.
5. HTTPS 터널 대상은 **`http://127.0.0.1:8001`**로 설정합니다. 코치용 8000으로 연결하지 않습니다.
6. 신뢰하는 로컬 터널/프록시만 8001에 접근하게 하고, 프록시가 `X-Forwarded-Proto: https`를 재설정하는지 확인합니다. 공유용 Waitress는 로컬 프록시의 해당 헤더만 신뢰하도록 설정되어 있습니다. 브라우저가 넣은 전달 헤더를 그대로 신뢰하면 안 됩니다.
7. 공통 HTTPS 주소를 전달합니다. 기본 `APP_OPEN_PORTAL=1`에서는 모든 활성 선수 이름·기록이 공유되며 누구나 이름을 선택해 업로드·비교·엑셀을 사용할 수 있습니다. 스마트폰 Wi-Fi를 끈 상태에서 확인하고, 수정·삭제·백업 같은 코치 기능은 차단되는지 점검합니다.
8. Windows 절전을 해제하고, 업데이트 재부팅 뒤 앱 두 개와 터널 재시작 방법을 정합니다. 자동 실행은 별도 설정이며 서비스로 자동 설치되지 않습니다.

공통 주소를 아는 사람은 별도 비밀번호 없이 전체 활성 선수 기록을 볼 수 있습니다. 이름 선택만으로 본인 확인은 하지 않습니다. 이 공유 범위를 선수·보호자에게 알리세요. 선수별 접근 제한을 원하면 `APP_OPEN_PORTAL=0`으로 전환하고 선수별 비밀 링크를 사용합니다. 개인 링크는 기본 90일 유효하며 재발급 시 기존 링크를 무효화합니다. 터널이 꺼지면 연결도 끊깁니다. 터널 계정 비밀키는 소스나 선수 링크 메시지에 넣지 마세요.

## 선택 B: Linux 인터넷 서버

PC를 꺼도 업로드해야 한다면 Python 3.12·지속 저장 디스크·HTTPS 프록시를 지원하는 VM/컨테이너 서버를 사용합니다. 무료 티어의 휴면·임시 디스크·업로드·트래픽·용량 제한을 확인하세요.

이 첫 버전은 SQLite 소규모 단일 배포 구성입니다. `DATABASE_URL`로 PostgreSQL을 자동 연결하는 기능은 없습니다. 다중 서버·많은 동시 쓰기는 PostgreSQL과 객체 저장소 지원을 별도로 구현·검증해야 합니다.

### Docker 예시

Dockerfile/Compose는 배포 출발점이며 실제 운영 호스트에서 검증해야 합니다. `.env`에 위 공개 주소·도메인·비밀키를 넣은 뒤 실행합니다.

```bash
docker compose up -d --build
docker compose exec web python manage.py createsuperuser
docker compose exec web python manage.py check --deploy
```

컨테이너는 로컬 코치 자동접속을 끕니다. 인터넷 서버에서 코치가 전체 관리를 하려면 위 명령으로 만든 코치 계정으로 로그인합니다. 선수는 기본 공통 주소에서 이름을 선택합니다. `APP_OPEN_PORTAL=0` 설정 시에는 개인 링크를 사용합니다. DB·원본은 `lesson_data` 지속 볼륨에 보관하고 기본 포트는 호스트의 `127.0.0.1:8000`에만 매핑됩니다. 여기의 8000은 **컨테이너 안에서 로컬 코치 모드를 끈 운영 서버**이므로 Windows 코치용 8000과 설정이 다릅니다.

호스트 HTTPS 프록시 Caddy의 연결 예시입니다. 소유한 실제 도메인과 DNS, 인증서 발급용 80/443 방화벽 설정이 필요합니다.

```caddyfile
lesson.example.com {
    reverse_proxy 127.0.0.1:8000
}
```

운영에서는 앱 포트를 외부에 직접 열지 않고, 프록시가 전달 헤더를 재설정하도록 합니다. Gunicorn은 기본적으로 로컬의 전달 헤더를 신뢰하므로 같은 호스트의 프록시를 전제로 합니다. 프록시가 다른 네트워크에서 접속하는 배포라면 그 주소만 신뢰하도록 별도 설정해야 합니다.

원본 업로드 폴더는 프록시의 공개 파일 경로로 제공하지 않습니다. 호스팅별 업로드 제한·시간제한·로그·비밀정보·백업 관리도 확인하세요.

업데이트 전 백업합니다.

```bash
docker compose exec web python manage.py backup_data --output /data/backup-before-update.zip
docker compose up -d --build
```

컨테이너 안의 백업만으로는 서버 고장에 대비할 수 없습니다. `docker compose cp` 등으로 안전한 별도 장소에 옮깁니다. `docker compose down -v`는 데이터 볼륨을 삭제하므로 일반 재시작에 사용하지 마세요.

### Docker 없이 실행

운영 환경변수를 `APP_LOCAL_COACH=0`, `APP_DEBUG=0`, `APP_SECURE=1`, `APP_TRUST_PROXY=1`과 실제 도메인·키로 설정한 뒤 실행합니다.

```bash
python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py collectstatic --noinput
python manage.py createsuperuser
gunicorn config.wsgi:application --bind 127.0.0.1:8000 --workers 1 --threads 4 --timeout 120
```

systemd 등 서비스 관리자에 실제 사용자·절대 경로·비공개 데이터 폴더를 지정합니다. Windows에서는 Gunicorn 대신 공유용 Waitress 스크립트를 사용합니다.

## 공개 전 점검

- 실제 HTTPS·정확한 도메인·고유 비밀키·보안 쿠키·프록시 헤더를 확인합니다.
- 외부 프로세스에서 `APP_LOCAL_COACH=0`이고 수정·삭제·백업 같은 관리자 기능이 차단되는지 확인합니다.
- 공통 모드에서 주소를 아는 누구나 전체 선수 기록을 볼 수 있다는 공유 범위를 알립니다. 비공개 모드라면 개인 링크와 폐기/재발급을 시험합니다.
- DB·업로드가 비공개 지속 디스크에 있으며 재시작 뒤 자료가 남는지 확인합니다.
- 스마트폰 이름 선택·업로드·비교·엑셀·백업 복구를 시험합니다. 비공개 모드를 사용할 때는 타 선수 접근 차단도 확인합니다.
- 미성년자 동의·보관기간·삭제 요청·PC 장애 대응 담당자를 정합니다.

도메인·터널·서버·저장소·백업·트래픽 비용이 발생할 수 있습니다. 실제 배포는 계정과 권한이 준비된 뒤 진행하며, 배포 예제가 있다는 것만으로 운영 배포나 Windows 실기기 검증이 완료된 것은 아닙니다.
